# Critic v11 — Design Editor — v1 plan

**Plan reviewed:** plans/v1/plan.md
**Date:** 2026-11-23
**Score:** 7/10 — the architecture, write-back and sync design are sound and very well defended, but nobody is assigned to run M0's hands-on checks while Ron is away, and M2 packs the whole properties panel into the critical path.

---

## TL;DR for Ron

The plan is solid. The core idea holds up: the canvas's own files are the document, edits are small splices, undo uses file snapshots, and a git three-way merge guards push. The security model (sandboxed second-origin iframe, a capability-URL prefix, a MessageChannel port as the probe's only channel) and the Windows byte-exactness rules are also unusually careful. The biggest risk is not technical. M0 is the gate for everything, several of its checks need someone to click through Claude Design (Save footprint, the Theme-menu write, the built-in editor inventory, a throwaway publish), and the plan says the kill bar is applied "with no pause for an answer" without saying who does that work or what to assume when it can't be done. Second, M2 is called the riskiest part but also carries the full panel UI (colour picker with oklch/P3, shadow list, typography, text-box trim, in-place text editing) in 2 days, and the cut list can't remove any of that. Ship after two small edits: give each manual M0 check a safe default, and split M2 so the write-back core lands first and the panel extras can be cut.

---

## Strengths

- **One document, no conversion** (Architecture, Write target). Inline `style` is the main write target, `<helmet><style>` is opt-in, and the cascade machinery is moved to Appendix A. That cuts the hardest failure mode (writing to the wrong rule) from the canvas path.
- **Undo by file pre-image plus a stored id map** (Undo). Byte-identical undo holds by construction, and no op kind needs its own inverse. That removes a whole class of bugs.
- **Writer shape check** (Writer, M5). Re-parsing after a structural splice and refusing parser fix-ups (`p` auto-close, nested `a`, foster-parenting) is the right guard. The same check runs again on merged files before push (Two guards).
- **Sync model** (Push steps 3-5). The Unison-style one-sided vs both-sided classification, `git merge-file` with stop-on-conflict, a single publish call, and a synced commit built from the bytes actually sent (`hash-object` + `update-index --cacheinfo`) together close the "lapsed lease after publish" and "edit during push" holes.
- **Security** (Scripts and trust). Opaque-origin sandbox on a second port, exact Host checks against DNS rebinding, a capability prefix so `Origin: null` plus `ACAO: *` can't read canvases, `Referrer-Policy: no-referrer`, and the port-as-capability handshake. All of it is reasoned against concrete attacks.
- **Build order as a walking skeleton** (Milestones). M0 → M1 → M2 → M6 proves the one external integration end to end before any manipulation UI exists, and the cut line follows that order.
- **Windows treated as a requirement, not an afterthought** (Cross-platform). Buffer-in/out, BOM kept, `* -text` in project repos, rename retry, leases instead of PIDs, `SIGBREAK`, and an `autocrlf` CI matrix.

## Concerns

### [major] M0's hands-on checks have no one to run them and no default while Ron is away  — §M0, §Goals (Kill bar)
**In plain words:** The first milestone is a fact-finding day, and several of its questions can only be answered by clicking around in Claude Design: change a property and Save, apply a theme colour, list what the built-in editor already does. Ron is away, and the plan says the go/no-go is applied automatically with no waiting, but it never says who does the clicking or what to assume if nobody can.
**What:** M0 lists "about ten separate checks, several needing hands-on work in Claude Design": the Save footprint (edit in Claude Design, Save, pull, diff), the Theme-menu write, the built-in editor inventory that drives the kill bar, the Artifact version-history check, and a publish → read round-trip on a throwaway copy, which first needs the copy recipe (create from `type_url`, publish, copy blobs server-side, rewrite ids, republish). The kill bar is "applied mechanically at M0's exit, with no pause for an answer". None of these checks has an owner (Claude by browser automation? Ron later?) or a default answer for when it can't be run. Ron's standing rule is to ask before each step on external accounts, and driving claude.ai's own editor UI is exactly that. The two-hour gate also includes the byte-exact publish round-trip, which depends on the whole copy recipe and on publish approvals.
**Why it matters:** Without an owner and a default per check, M0 either stalls (the gate never clears, so M1 never starts) or gets "answered" by guesswork that the plan then treats as measured fact. That's the very thing the fixed branches were meant to prevent. The Save footprint decides whether `node-diff3` is in v1, the inventory decides how much of M3-M5 survives, and the Theme write decides M5's token form.
**Best-practice options:**
1. **Give every M0 check an owner and a worst-case default fixed before M0 runs.** *Plain words: decide now what to assume for each question nobody can answer today, choosing the answer that costs the least if it turns out wrong.* Split the checks into (a) ones Claude can run itself, either read-only or through the Artifact tool on a throwaway copy (pull, `data-ed-id` survival, runtime under the serving layer, publish → read round-trip, partial publish, offsets on LF/CRLF/BOM), and (b) ones that need a person in Claude Design (Save footprint, Theme-menu write, built-in inventory, version-history UI). For (b), fix defaults now: Save footprint = "large" (turn on the token-level `node-diff3` retry, about ½ day, so the merge stays safe either way); built-in inventory = "as documented" (snapping, Alt-measure and handles are "not stated", so go as planned); Theme write = the `:root`/`var(--x)` fallback already written in M5. Record each default as "assumed, Ron to confirm" in `06`. A spike is a fixed time box that ends in a decision even when uncertainty remains (Mike Cohn, "Spikes", https://www.mountaingoatsoftware.com/blog/spikes). Cost: about ½ day of possibly unneeded `node-diff3` work. The gain is that M0 finishes unattended.
2. Run the (b) checks through browser automation on claude.ai. *Plain words: let Claude drive Claude Design's UI itself.* This answers the questions for real, but it acts on Ron's account without his per-step OK, against his standing rule, and the UI may change. I wouldn't pick it while he's away.
3. Defer the (b) checks to Ron's return and block M1 until then. *Plain words: wait.* Safe, but it stalls the whole project for checks whose worst-case answers are already cheap to plan for.

I'd pick option 1: each default costs at most ½ day if wrong, and it keeps M0's "branches fixed in advance" promise honest.

### [major] M2 is "the riskiest part" but also carries the whole properties panel, and the cut list can't reach it  — §M2, §Effort
**In plain words:** The milestone that proves edits are written back safely is also where the colour picker, shadow editor, typography controls and in-place text editing get built, all in two days. If it runs long, the plan says to cut later features first, but the bulk of M2's work is panel polish that can't be cut, so the risky core and the nice-to-haves slip together.
**What:** M2 (2 days) contains the PatchEngine for four op kinds, Writer, Watcher, UndoLog with id maps, the `<helmet><style>` minimal rule lookup and the `getComputedStyle` gate, byte-exact CRLF/BOM handling, *and* the editable panel: number inputs with unit preservation, a colour picker that keeps `oklch()`/`color(display-p3 …)`, opacity, radius, border, a shadow list, typography, a text-box trim toggle, plus `contenteditable="plaintext-only"` text editing with a `MutationObserver` cancel path and `setText` entity-preserving splices. The Effort section says "M2 is the critical path. If it slips, cut M5's layer actions", and the cut order inside v1 is M5 layer actions → multi-edit → text-box trim. Only text-box trim comes from M2. M1 (2-3 days) is similarly dense: server, SourceIndex, serving transform, MessageChannel probe with per-frame batching, zoom/pan, the Interact toggle, the template-tree layers panel, two-OS CI and the mockup check.
**Why it matters:** The cut line ships v1 once M0, M1, M2 and M6 are green. If M2 overruns, M6 (the sync loop and the only external integration) is pushed back, while M5 cuts don't recover M2 time because M5 is built after M6. A slip in panel widgets therefore delays the parts the cut line is meant to protect.
**Best-practice options:**
1. **Split M2 into M2a "write-back core" and M2b "panel controls", and put M2b items on the cut list.** *Plain words: build the part that has to be right first, and make the polish removable.* M2a = PatchEngine, Writer, Watcher, UndoLog, number inputs with units, a hex/alpha colour field that preserves the authored text, and single-text-node editing, and its exits are the M2 golden/zero-byte/CRLF/locked-file tests. M2b = the shadow list, the full typography section, the oklch/P3 picker UI and text-box trim, built after M6 alongside M3 and cut before M5. The build order becomes M0 → M1 → M2a → M6 → M2b → M3 → M4 → M5. This follows the walking-skeleton rule of completing the end-to-end path at minimal width first (Henrico Dolfing, "Start Your Project with a Walking Skeleton", https://henricodolfing.com/2018/04/start-your-project-with-walking-skeleton.html) and Shape Up's marking of nice-to-haves (~) so they're the first thing hammered (Basecamp, Shape Up ch. 14 "Decide When to Stop", https://basecamp.com/shapeup/3.5-chapter-14). Cost: one plan edit, no new code.
2. Keep M2 whole but re-estimate it at 3-4 days now. *Plain words: admit it's bigger.* This is honest, but it still couples M6's start to panel polish.
3. Leave as is and rely on the post-M0 re-estimate. *Plain words: fix it later.* The re-estimate changes numbers, not what is cuttable.

I'd pick option 1: it protects M6 without dropping any feature from v1.

### [minor] The kill bar can never stop the project  — §Goals (Kill bar), §M0 Exit
**In plain words:** The plan says "stop the project if nothing this editor adds survives", but two of the things on that list (git diffs and offline editing) always survive by construction, so the stop can never fire. That's fine if intended, but then it's a scope-shrink rule, not a kill bar, and it should say so.
**What:** The stop condition requires that "none of snapping, Alt-measure, Auto Layout handles, Hug / Fill / Fixed, token binding, git line diffs or offline editing survives". M1, M2 and M6 are "always kept", and they deliver git line diffs and offline editing, so the condition is unreachable. The M0 exit's "if that list is empty, stop" is unreachable for the same reason. Line-level git history of Claude Design edits would also come from M6's pull/push alone, without a canvas editor.
**Why it matters:** Ron reads "kill bar" as a real off-switch. If M0 finds every precision feature already built in, the plan still spends M1 + M2 (4-5 days) on a canvas whose remaining value is offline panel editing, and no one has weighed that against the cheaper floor of shipping only the sync tool.
**Best-practice options:**
1. **Rename it to a "scope floor" and state the floor explicitly.** *Plain words: say plainly that M0 can only shrink the plan, and name the smallest thing that still ships.* If M0 finds every precision feature built in, the floor is M6's `edsync` pull/push (git history of Claude Design edits) plus M1 + M2, and M0's `06` note records the case for and against keeping M1/M2 for Ron to confirm. This is a local wording fix; no external pattern was relevant beyond the spike rule that a time box ends in an explicit decision (Mike Cohn, "Spikes", https://www.mountaingoatsoftware.com/blog/spikes).
2. Make it a real kill bar: if all precision features exist, ship M6 only and move M1-M5 to Next. *Plain words: build only the sync tool.* This saves the most days, but it reverses Ron's recorded "M1, M2 and M6 are always kept" while he's away.

I'd pick option 1, the conservative one: it keeps Ron's decision and only makes the text honest.

### [minor] The Artifact tool's contract already answers one M0 question, and the pull hand-off skips a step  — §Pull / push (Hand-off contract, Two guards), §M0
**In plain words:** The plan asks M0 to find out whether a multi-file publish can half-succeed, but the publishing tool's own rules already say it can't. And the pull step reads "every file" in one call without first asking the tool which files exist.
**What:** The Artifact tool contract (as exposed in this session) says that for a publish with `files`/`root`, every touched path must have been read, listed or published and must not have changed since, "otherwise nothing is sent and the refusal names each path". So a stale file rejects the whole call, which is what push's single-publish design assumes. Separately, the hand-off says the skill reads "every `project/*` file plus `canvas.json` in one Artifact `read` with `paths`", but `paths` needs the names up front. That takes a `list` with `scope: "files"` first (which also counts as "saw in a file listing" for the freshness rule). The plan also mixes `canvas.json` and `project/canvas.json`.
**Why it matters:** These are small, but the hand-off is the one place the skills hold behaviour, and a missing list step would make the first unattended pull fail.
**Best-practice options:**
1. **State the contract and add the listing step.** *Plain words: write down what the tool already guarantees and add the missing "list files" call.* Pull step 1 and push step 2 become: `list` (`scope: "files"`) → `read` with those `paths` → `edsync ingest`/`classify`. Record the documented all-or-nothing refusal in `06` as the expected answer, and keep the M0 partial-publish check only as a confirmation. Always use `project/canvas.json`. Local fix; no external pattern applies.

### [minor] The mockup screenshot check has no pass rule  — §Stack (UI design), §M1 Exit, §M7 Exit
**In plain words:** The plan says the editor must "pass" a side-by-side screenshot comparison with the chosen mockup, but the mockup is a static page with made-up content, so a pixel comparison will always fail, and "looks close enough" isn't a test.
**What:** M1's and M7's exits require "the side-by-side screenshot check against the chosen UI mockup", with no criterion. The M1 exit also still says "(once picked)", although B is picked. A literal image diff between the mockup HTML and the live editor (different content, fonts, live canvas) cannot pass, so in practice this becomes a subjective call, made by the same agent that built the UI.
**Why it matters:** An exit criterion nobody can fail adds no assurance, and one nobody can pass blocks a milestone. Either way it can't be checked mechanically while Ron is away.
**Best-practice options:**
1. **Split it into a checked list plus a self-baseline.** *Plain words: compare the things that must match (layout, colours, key components) one by one, then freeze the editor's own screenshot so later changes are caught.* Write a short checklist taken from `b-warm-studio.html`: panel positions and widths, the token colours read from its CSS variables, the clay accent only on selection/active/Push, the shared-class chip, the toast with Undo + Diff, dark and light themes. Check the items via computed styles in Playwright, then lock the editor shell with Playwright `toHaveScreenshot` against its own baseline (`threshold`, `maxDiffPixels`) so regressions are caught at M7 (Playwright, "Visual comparisons", https://playwright.dev/docs/test-snapshots). The human side-by-side stays as a note for Ron.
2. Keep the side-by-side as a manual review only and say so. *Plain words: a person looks at it.* This is honest but can't be run while Ron is away.

### [minor] Leftover and inconsistent text from earlier rounds  — §Open questions, §Goals, §Architecture, README
**In plain words:** After many revisions, some sentences still describe the older plan, and a builder who takes them literally will build the wrong thing.
**What:** (a) Open question 1 says Test Site's shape "exercises shared-rule targeting, cross-file indexing" — plain-HTML branch features that are inactive on canvases. (b) The kill bar says git diffs and offline editing matter per "Goals 2 and 4", but Goal 4 is cross-platform. (c) The Architecture diagram labels the editor `localhost:5300`, while Stack and Cross-platform say to bind and use `127.0.0.1`. (d) The README promises "Warns before you touch a class shared by other elements", which is Appendix A only. (e) Many paragraphs carry three to five stacked `(decided: …)` tags, and the Kill bar and Scripts and trust paragraphs run 250+ words, with rationale woven into instructions, so it's hard to tell the rule from its history.
**Why it matters:** The plan is going to an agent-driven implementation (`deep-implement`), which reads text literally. A stale sentence in an 89 KB plan is how a branch marked inactive gets built.
**Best-practice options:**
1. **One cleanup pass: fix (a)-(d), and move rationale and decision history into a short decision log at the end.** *Plain words: keep the plan as the instructions, and put the "why and when decided" in a separate list.* Each log entry gets title, context, decision and consequences, and superseded entries stay marked as superseded (Michael Nygard, "Documenting Architecture Decisions", https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions; ADR community, https://adr.github.io/). Cost: about an hour, and no design change.
2. Fix only (a)-(d) and leave the inline tags. *Plain words: just correct the wrong sentences.* This is cheaper, but the readability problem stays.
